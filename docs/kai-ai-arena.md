# 修掉 4 个 bug 后，我测出的“模型个性”塌了一半

### 一款大话骰游戏，为什么会长出自己的 AI Arena

> 本文由 AI 协助整理。项目细节、实验数据和结论均来自《开！》的代码、设计记录与真实 API 跑批。文中对模型的描述只适用于这张桌子和对应样本，不代表通用能力评价。

---

2026 年 8 月 7 日晚上 7 点 11 分，《开！》有了第一次提交。那时仓库里还没有排行榜，也没有 AI Arena。我想先做一局能跑通的大话骰：对面坐着一个大模型，它看自己的骰子，听玩家报价，然后决定继续加码还是开牌。

四分钟后，规则引擎的第一版已经进了仓库。当天晚上接入 DeepSeek 后，模型能够完成一整局。它和人类玩家走同一套座位接口：

- `observe()` 返回自己的骰子和公开事件；
- `act()` 接收这个座位提交的动作。

接口里没有对手骰面字段，模型自然无从读取。信息隔离由数据结构完成，人类 UI 和模型客户端也共用同一条结算路径。这样一来，模型对局、真人对局和后来的自对弈都能复用同一份事件记录。

能打完一局只是起点。我希望它在多打几局以后改变判断，于是又加了跨场档案。引擎写可复算的事实，例如玩家开过几次牌、虚报发生在哪几局；模型写自己的观察，例如“他在高倍率时更保守”或者“这次停顿可能是在装弱”。玩家可以翻开这份档案，模型下一次再遇见玩家时也会读到旧记录。

## 第一个对手叫老李头

第一天的版本里，模型并没有直接用型号名称出现。它扮演一个叫老李头的牌桌老板：要面子、记仇、自负，说话还有固定腔调。我给他写了策略倾向和性格缺陷，希望玩家能很快认出这个对手。

效果来得很快。台词有戏，输赢也像一场完整的角色对局。可在接入更多模型后，一个问题越来越难回避：桌上的区别究竟来自底层模型，还是老李头这套提示词？如果每个型号都按同一份角色剧本说话，换模型对于玩家可能只剩速度和价格变化。

8 月 9 日，项目进行到第三天，我删掉了老李头。名字、腔调、嘴臭度、性格缺陷和策略染色陆续退出提示词。所有席位开始使用逐字相同的 system prompt，模型连自己的展示名称都不知道。

提示词只保留规则、动作格式和已经发生的事实。“多观察对手”“大胆一点”“做你自己”也被清掉了。这些话看起来没有指定性格，仍会改变模型关注的信息和行动尺度。

删人设带来的损失很直接。模型可能沉默，也可能打得很稳却没有戏；项目此前积累的角色资产也随之作废。留下来的产品设想更难实现，但口径清楚了：玩家看到的对手名称就是底层型号，桌上的差异需要由模型自己的行为支撑。

## 游戏里多了一张素颜桌

同一天，我开了一条“素颜擂台”实验。它要回答的产品问题很具体：底层型号更换以后，报价习惯、开牌阈值、说话方式和反应节奏会不会出现稳定变化。

实验把两个模型接到现成的玩家接口上，让它们自己打完整场。每副骰连续使用两次，模型交换座位；提示词、采样参数和规则版本固定。游戏里的跨场档案暂时关闭，因为上一场留下的判断会改变下一场条件，不适合直接混进横向比较。

这张桌子起初只是一个跑批脚本。随着记录的项目增多，它才逐渐有了榜、实录和审计工具。后来我开始叫它 AI Arena。

## 三组指标回答三个问题

胜率计算简单，也很容易被误用。它能告诉我谁在这套规则下赢得更多，却无法说明两个模型是否像不同的对手。

因此，Arena 的指标分成三组：

| 层级 | 记录内容 | 回答的问题 |
|---|---|---|
| 合规 | 非法动作、格式失败、拒绝、降级顶班 | 模型能否正常完成比赛 |
| 棋力 | 胜率、开牌命中、净筹码、必败开牌 | 模型在这张桌子上打得怎样 |
| 风味 | 虚报、蒙报、抬价深度、bait、台词、出手节奏 | 换型号后，打法是否发生可感知的变化 |

“换模型等于换对手”依赖第三组数据。合规和棋力也很重要，只是它们在回答另外两个问题。把三组数据揉成一个总分，API 兼容性和解析失败很容易混进所谓的模型气质。

跑批时还有几项固定条件：同一份提示词、同一采样参数、同一套引擎；每副骰打两遍，双方交换座位；实验用途锁定供应商路由。用于横向比较的素颜赛道关闭跨场记忆，避免前一场留下的档案改变后一场条件。

这些规则后来一条条写进批次记录，因为第一批约 60 场比赛已经证明，口头上的“公平对比”远远不够。

## 第一批数据先暴露了四处实现问题

8 月 10 日，第一批约 60 场比赛跑完。DeepSeek V4-Pro 有将近四成报价发生在看骰之前。大话骰允许盖着骰盅报价，这种动作风险很高，很容易被读成一种鲜明打法：相信直觉、敢赌、喜欢用气势压人。另一边的模型更常先看骰、再计算，两者看上去已经分开了。

检查上下文时，我发现模型即使没有主动计算，系统仍会提供粗略概率，动作候选还按概率排好了顺序。它盖着骰盅也能获得很强的决策暗示。清掉这处信息泄漏后，V4-Pro 的蒙报率从约 **40% 降到约 6%**。

桌上那个“凭感觉下注的 DeepSeek”随之消失。继续排查下去，又找到三处会影响行为解释的问题：

| 实现问题 | 数据当时呈现的样子 | 修复后的变化 |
|---|---|---|
| `max_tokens=400` 截断长输出 | 某模型经常格式失败，需要 bot 顶班 | 格式失败和顶班明显下降 |
| 未主动计算也会收到粗档概率，候选动作按概率排序 | 某模型经常不看骰报价 | 蒙报率约 40% → 约 6% |
| 擂台没有转发对手台词 | 某模型胜率很低，也不会回应对手 | 恢复台词后，胜率回到约 40%–60% |
| 主观判断入库时只保留前 100 字 | 某模型的留档跳跃、混乱 | 保存完整文本后，原有判断链重新出现 |

它们没有让任务彻底报错。长输出被截断以后，沉默 bot 会接管；模型听不见对手时，仍能根据报价继续行动；档案被截短，也不影响下一场启动。比赛能够结束，排行榜照样会生成。

这种“能跑完”的状态很容易让人放松警惕。

有一次，中文内容被放进 HTTP 请求头，引发 ByteString 异常，整个模型通道随之失效。降级 bot 稳定接管了比赛。如果榜单只记录最后的胜负，我只会看到一名异常沉默的选手，很难想到它其实根本没有参赛。

供应商路由也会造成类似问题。同一个模型 ID 可能落到不同后端或量化版本；请求参数收到 HTTP 200，也不保证推理开关和 token 上限已经生效。上一篇 DeepSeek 文章中的空回复和预算失控，便来自这条链路。

于是，顶班率、格式失败率和实际 reasoning token 都被放到比分旁边。每个批次同时保存 prompt 版本、system prompt 哈希、采样设置、路由限制和代码提交。判断实验条件时，我开始依赖调用回执和落盘记录，不再依赖请求参数表达的意图。

首批约 60 场数据最终留下了一个尴尬的结果：几项原本显眼的风味差异在修复后大幅收拢，只剩“使用概率工具的频率”仍有明显区别。后来概率工具从游戏中删除，这条指标也失去了产品意义。

到这里，“不同型号足以成为不同对手”既没有得到证明，也没有被推翻。Arena 清掉的是几条过早的解释。

## 擂台上的问题也回到了玩家桌上

概率工具的删除便是其中一次回流。

早期版本给人类和模型都提供精确概率。它确实对称，也能减少算错，但试玩很快变成了看表决策：概率低就开，高就继续报价。玩家省下了计算，也一并省下了判断。

我先把计算器改成每局一次的公开动作，希望“什么时候算”能成为新的牌桌信号。后来的模型对局又显示，有些模型在调用工具之前已经能手算出正确概率。计算器提供的信息增量很小，公开拨算盘反倒像一套由产品设计出来的表演。

最后，人类和 AI 的概率工具一起被移除。它们可以心算，也可以算错，错误本身会进入打法。

另一次回流来自 `say` 字段。它最初的说明只有“台词，上屏”。模型几乎每手都填写，但很多内容像写给系统的备注，很少回应对手。说明改成“当众说，全桌都听得见”以后，另一个模型又突然变得拘谨，开口率和平均句长一起下降。

最终版本写成了“说给对手听的话”。它只说明牌桌上的事实，不解释“上屏”“存档”这些产品实现。这个小字段改了几轮以后，项目里的提示词也采用了同样的写法：描述模型身处的环境，界面和数据管线留给代码处理。

Arena 在这里承担了回归测试的作用。每次改提示词、动作候选或推理预算，都可能重新塑造桌上的行为；旧批次也会因此失去可比性。冻结版本逐渐成为实验流程的一部分。

## 记忆对局另开一条赛道

横向比较希望每场条件独立，游戏体验却依赖跨场档案。这两个目标放在同一批数据里会互相干扰，因此 Arena 分成了两条赛道。

素颜赛道关闭记忆，用来比较合规、棋力和风味。记忆赛道允许模型沿着系列赛建立对手档案，观察判断如何形成，又会怎样影响下一场。

在一组 5 场的早期系列赛里，DeepSeek 和 Kimi 分别整理出了对方的行为规律。两边最后得到的画像相当接近：一方首报通常偏实，另一方嘴里说出的概率不太可靠。还有一个模型注意到，对手已经把自己记成了某种人，于是开始考虑如何维持或利用这个形象。

这个现象符合游戏最初设想的二阶互动，但样本只有 5 场。目前它只能说明这条链路确实出现过，还不能说明它稳定存在，更不能用于型号排名。

两条赛道因此保留不同用途。素颜赛道尽量排除历史，方便重跑；记忆赛道保留路径依赖，接近玩家实际遇到的对手。它们共用引擎，数据不混在一起。

## 这张桌子目前能说明多少

当前干净集包含 7 个型号、11 组对手关系、22 个座位臂，共 44 场比赛。这个规模足以发现明显的实现污染，也能筛出值得继续扩样的现象。拿它给模型做通用排名，证据还差得很远。

大话骰本身提供了不错的观察条件：每个动作都能验证合法性；模型需要处理隐藏信息；语言会被对手听见并影响后续；每局开牌后，先前的判断可以回看。记忆加入以后，对手还会针对档案反装。

与此同时，结果高度依赖游戏规则、提示词、推理设置和服务商路由。榜单因此始终使用“在这张桌子上”的口径，每项比率附上自己的分母。胜率旁边保留失败和降级数据，也比做一个总分更有用。

我最初建 Arena，是想尽快确认不同模型能否撑起不同对手。现在还没有足够数据回答这个问题。它已经帮我删掉了几条错误答案，也迫使游戏修改了概率工具、台词契约和批次记录方式。

回头看这段开发过程，游戏和 Arena 的分工很简单：玩家桌上出现一个有趣行为，擂台负责追查它从哪里来。如果差异在换座、重跑和修复污染以后仍然存在，才值得写进对手介绍。要是最后分不开，“换模型等于换对手”这项产品假设也应该被撤掉。

现在打开排行榜，我会先看顶班率和格式失败率，再看 prompt、路由与推理设置是否一致。确认参赛者真的打完了同一场比赛以后，胜负才有解释的价值。
